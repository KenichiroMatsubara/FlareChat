# Plan every Automation Rule Run before applying its effects

> Mailbox Test paragraphs are superseded by ADR 0136; the Rule Execution decisions remain in force.

Every Automation Rule type has the same three Execution Modes: read-only, approval, and unattended. Unattended execution is the defining capability rather than a shortcut around an approval-based design, so one deep Rule Execution module first plans a Rule Run's complete set of Rule Effects and only then applies that frozen plan according to its mode. The module records a common immutable Rule Run for Schema Rules and Agent Rules; read-only retains the plan, approval holds it, and unattended applies it immediately.

Live orchestration begins with one persisted Source Message, selects the eligible Active Schema and Agent Rules, and hands each selected Rule Revision's complete plan to Rule Execution. A Draft preview names one Rule Revision but still evaluates its Selection Policy before planning. Rule Execution owns the immutable Rule Run and Rule Effects, mode dispatch, approval decisions, and resumption; cron, Mailbox Test, and HTTP callers do not implement those policies independently.

Planning may persist Source Message intake, the Rule Run, Proposed Actions, and diagnostic records, but it causes no Rule Effect. Tasks, Guest Registrations, Scheduled Event projections, Drive publications, Recipient Snapshots, Delivery Records, and provider writes all belong to the apply side of the seam. Approval uses the same plan as unattended: every Proposed Action from one Rule Run is approved or rejected as one batch, no AI or policy is rerun after approval, and changed external preconditions fail rather than silently changing what the Admin reviewed. Provider-generated identifiers and URLs may flow mechanically between dependent effects without becoming a new decision.

Each Rule Effect has a stable idempotency key and its own outcome. After apply begins, the Rule Execution module automatically resumes only incomplete effects with transient failures, never resends a successful effect, and never replans the run; bounded permanent failure becomes an Automation Exception. An approved run uses the same recovery policy as an unattended run, so human confirmation is not a recovery mechanism. The module exposes resumption as an operational use-case alongside starting a run and deciding an approval batch.

Rule Effects form an internal dependency graph. A failed effect blocks only its descendants, such as a Calendar write that needs a Drive publication's URL, while independent effects continue; callers and tests observe effect outcomes without learning the graph representation. This contains partial provider failure without turning an unrelated successful branch into work for an Admin.

Before a plan is frozen, the same Rule Run may automatically retry transient AI and provider-read failures under a bounded retry policy. Invalid rule configuration or an extraction that cannot satisfy validation fails permanently instead. Proposed Actions become visible only when the complete plan succeeds; after that freeze, neither retry nor approval may invoke AI, selection, correlation, or routing again.

Agent Rule write tools also plan before they apply. Read-only omits them; approval and unattended both record the complete tool arguments and return a planned result to the model, then only after the model finishes does approval wait or unattended apply the frozen actions. The model never observes provider write results or makes a later decision from them, consistent with ADR 0110's finding that intended Agent Rules do not need that feedback.

An approval batch expires seven days after its plan is frozen, retaining ADR 0110's existing bound. Expiration ends the entire batch and cannot be reversed; applying the Source Message later requires a new Rule Run. A Mailbox Test may use a short-lived encrypted handoff between its extraction response and Draft-run creation, but that handoff is neither an approval record nor an executable Calendar command; the persisted Rule Run is the reviewed artifact, while audit retention remains a separate policy.

Rule Runs becomes the Admin-facing history and review surface for both rule types and all three modes, including approval batches. Mailbox Test remains only as the operation that starts a Draft Schema Rule Revision against one selected Source Message through the same Selection Policy and planning implementation as live processing; a non-matching Source Message stops before extraction and no Draft run applies effects. Its former rule-free Calendar creation is removed. Event Refresh is separate because it is a manual repair exit that deliberately overwrites Manual Overrides, which ordinary Rule Execution never does.

The administration GUI therefore gives Event Refresh its own page and keeps it out of Rule Runs. That page retains the deliberate Source Message re-extraction, correspondence review, diff, and forced rewrite flow; a future Scheduled Events view may invoke the same repair module without moving the capability back into Rule Execution.

Existing Schema Rules migrate to `unattended`, preserving their current behaviour. New Schema Rules and Agent Rules both default to `Draft + unattended`: Draft prevents effects until explicit activation, while activation does not introduce a hidden human dependency. Admins may explicitly select read-only or approval before activation. Existing Agent Rules keep their current Rule State and Execution Mode.

This expands ADR 0110's Execution Modes and Proposed Actions from Agent Rules to every Automation Rule type. ADR 0106's separate Schema Rule and Agent Rule tables remain: sharing Execution Modes and Rule Execution does not make one rule type a mode of the other. It also supplies the rule-bound Draft preview promised by ADR 0061.

Rule State and Execution Mode are independent for both rule types, so Agent Rules also gain Draft. This supersedes ADR 0110's consequence that approval mode replaces an Agent Rule Draft: Draft governs whether a rule is eligible for live execution and supports no-effect preview, while approval governs what happens to a live run's planned effects.
