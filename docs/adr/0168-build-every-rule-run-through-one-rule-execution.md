# Build every Rule Run through one Rule Execution

A Rule Run is started, decided, resumed, expired, listed, and read through one Rule Execution built once per Account, as `ruleExecutionFor({ env, database, accountId })`. The module that ADR 0134 asked for existed in `execution.ts`, but only half of its interface was inside it: every caller had to assemble the planner and the Rule Effect port itself, so the port was rebuilt at five call sites and Operator Chat inserted its Rule Run rows without touching the module at all. The three inline copies of the effect-kind switch had already diverged — the copy that resumes due effects could not apply the email-summary effect ADR 0165 added, so an approved run that met one transient failure was never resumable. This is the failure a deep module exists to prevent, and it happened because the module was not deep enough.

What varies per run is the plan, so the planner is an argument of `start()` rather than of the module: a Schema Rule's extraction, an Agent Rule's planned actions, a Draft preview, and an approval decision each hand Rule Execution their own plan and nothing else. What does not vary per run is how an effect is applied once the Account is known, so the Rule Effect port disappears from every caller and is built inside the module: the effect-kind switch, the Schema and Agent write ports, the Automation Inbox token, and the read-side state changes a completed run makes to its Source Message all live there. Tests reach the same behaviour through `start()`; only a test that needs to observe effects being applied substitutes the internal port, and that seam is not part of the interface.

A Rule Effect is one planned mutation, so each effect kind carries exactly the arguments that mutation needs, as one discriminated union that the switch exhausts: `schema.record_warnings`, `schema.create_tasks`, `schema.apply_events`, and `schema.deliver_summary` each hold their own slice of the extraction rather than four copies of the whole, and `agent.send_line_message`, `agent.send_email_summary`, and `agent.create_scheduled_event` hold the tool's arguments. Effects are decoded and validated from D1 in one place. A new kind that is not handled fails to compile, which is the check whose absence let the resume copy drift.

The Agent write port that `runAgent` receives is never called during the model's turn, because ADR 0134 returns a planned result to the model and applies afterwards; it was the apply-side half of the Agent effects under another name, so it folds into Rule Execution and leaves `runAgent`'s interface. Execution Mode is enforced at two places by design and no more: where tools are bound, per ADR 0142, and where a frozen plan is applied or held, inside Rule Execution. Attachment contents that the intake already read from Gmail reach the apply side through a reader that Rule Execution memoises by Gmail message for its own lifetime, so the production path keeps its request count and nothing about the optimisation appears on the interface; a run resumed on a later day reads them again. Operator Chat records its exchange as a Rule Run through the same module, as ADR 0146 promised, rather than through its own insert.

## Consequences

`execution.ts` grows and `automation.ts` and `api.ts` each lose a dispatcher; the approval route calls the same module the cron does. Source Snapshots of ADR 0011 remain unimplemented and are not made a dependency of this change: apply-side attachments come from the memoised Gmail read, and a durable copy is a separate decision.
