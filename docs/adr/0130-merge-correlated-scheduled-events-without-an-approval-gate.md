# Merge correlated Scheduled Events without an approval gate

Every Scheduled Event insertion becomes an upsert. Before a Source Message's Event Candidates reach Google Calendar they are correlated against the events already there, and a correlated candidate merges into the existing event field by field instead of creating a second one. ADR 0012 promised this lifecycle and never built it: the automation path posted one new Calendar event per candidate unconditionally, so a follow-up message about a meeting produced a second meeting.

The correlation is the AI correspondence of ADR 0123, reused. Gmail thread identity was considered as a cheaper, deterministic key and rejected as the primary one, because the messages that duplicate an event most often are not replies: a forwarded invitation, a correction sent as a fresh message, a re-announcement from a second sender, and a thread split by an edited subject all arrive outside the original thread. A key that covers only replies would push every one of those into a permanent exception list.

Nothing waits for an Admin. ADR 0123 made its correspondence a proposal because an Event Refresh already has an Admin in front of it; inbound automation is unattended by ADR 0001, and an approval queue there would simply stop the automation. The hazard that gated it is real all the same — a `PATCH` keeps the event's attendees — so the approval is replaced by mechanical limits rather than removed. The seven-day correspondence bound of ADR 0123 is carried over unchanged and still discards a distant match however confident the AI was, which converts the unrecoverable failure, an existing invitation list moved onto a different meeting, into a recoverable one: a duplicate event an Admin can delete.

The merge compares against Google Calendar's current state, not against the `events` row Mail Automation last wrote. A Manual Override may be made directly on the organizer's calendar, and `event_overrides` records only overrides made through the GUI, because it requires an actor identity. Comparing against D1 would therefore leave a time an Admin fixed on their own calendar absent from the comparison entirely and overwrite it every time, while logging the write as a success. Comparing against Calendar makes the difference between the two the evidence that a human touched the field — evidence obtained without asking a human anything, which is what an unattended path needs.

That evidence locks fields, not events. A field whose Calendar value has diverged from the value Mail Automation last wrote is excluded from the merge and the remaining fields still update. This is the literal reading of the Manual Override rule — `automated Event Changes may not overwrite` — so it creates no second exception to it. Freezing the whole event on the first divergence was rejected: a corrected typo in a title would make the automation ignore a genuine venue change forever, and under an unattended design a silent refusal to update is as damaging as a silent overwrite.

## Consequences

`canApplyCalendarUpdate` takes `hasManualOverride` as one boolean for the whole event and now needs a set of locked fields instead. The `events` table carries no ETag column, so the Calendar Revision that CONTEXT.md already defines has to be stored before a merge can hold an optimistic lock on its write.

A correspondence beyond seven days still produces a duplicate Scheduled Event. That is the deliberate trade of ADR 0123, kept here: an Admin deleting a stray event is the price of never moving a real meeting's invitation list.
