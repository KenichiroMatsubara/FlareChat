# Rehearse every migration against production before merge

Migration 0030 stopped production. It rewrote reminder Jobs from the `contactId` in their payload, and four rows queued before the rename of ADR 0157 carried `memberId` instead; the key it built was NULL, the NOT NULL column refused it, and every request that reached Database Access retried the same failing statement. The release barrier of ADR 0100 would have stopped that deploy before it happened, but the barrier had never run: the deployment's actual deploy command was `wrangler deploy`, so the runtime repair path that ADR 0100 names as a fallback had been the only migration mechanism since August, and a fallback that fails is a full outage. Nothing between a pull request and production had asked whether the migration worked on the rows production actually holds, and nothing had noticed that the release command was not the one being run.

A migration is a contract with production data, and the only test of that contract is production data. From now on every pull request and every release rehearses the pending migrations: each D1 database the deployment owns is exported, replayed into SQLite, and taken to the schema target by the same Schema Lifecycle the Worker and the fleet release use. A rehearsal that fails makes the pull request unmergeable and makes `deploy:cloudflare` stop before it touches a production database. The rehearsal is the first step of the release command, ahead of the barrier, so a migration that would fail mid-fleet never leaves the barrier held. Production is deployed only through `deploy:cloudflare`; a deploy command that skips it is a configuration defect, and the barrier row in Control D1 is the evidence of whether the command is being run.

## Consequences

Pull requests need the rehearsal check green before they merge, and the check needs a read-scoped Cloudflare token in the repository's secrets. A migration author reads the history of every field the migration touches, because rows written under an earlier shape are still there, and writes the migration so that no row can make it fail: coalesced key parts, `UPDATE OR IGNORE` where a rewrite may collide, and a `json_valid` guard before any JSON function. The rehearsal also proves a checked-in migration file still matches its recorded checksum in production, so an edit to a released migration fails here rather than in the Worker.
